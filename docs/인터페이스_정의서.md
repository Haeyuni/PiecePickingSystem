# 인터페이스 정의서: sort_msgs

BR 문서·시스템명세서에 정의된 5계층(인지·파지·계획·실행·웹)이 실제로 주고받는 ROS2 메시지·액션·설정 파일의 스키마를 확정한다. 이 문서가 확정되면 각 계층은 서로의 내부 구현을 몰라도 이 인터페이스만으로 개발을 진행할 수 있다.

| 항목 | 내용 |
| --- | --- |
| 문서 버전 | v2.1 (2026-09-10 — 메시지·액션 정의를 `src/sort_msgs`의 실제 파일과 동기화, `SelectedGrasp` 절 추가, `bins.yaml` 스키마를 box geometry 실측 형식으로 갱신) |
| 대상 패키지 | `src/sort_msgs` (ament_cmake), `perception`/`grasp`/`control`이 참조하는 `objects.yaml`/`bins.yaml` |
| 관련 문서 | BR 문서, 시스템명세서 |

---

## 1. 공통 필드 규칙

`perception`, `grasp`, `control`, `planner`, `web`은 각각 독립 컨테이너로 배포된다. 한쪽만 재빌드되고 다른 쪽이 안 바뀐 상태로 통신하면, 필드가 어긋난 채 조용히 잘못된 값을 주고받을 수 있다. 아래 네 필드는 이 문제를 막기 위한 것이며, **모든 메시지에 일괄 적용하지 않고 아래 기준에 따라 선택적으로 붙인다.**

| 필드 | 규칙 | 적용 대상 |
| --- | --- | --- |
| `schema_version` | 하위 호환 변경은 minor, 비호환 변경은 major 증가 (예: `"1.0.0"`) | **독립적으로 주고받는 최상위 메시지**(`WorldState`, `InstanceMasks`, `Pick`/`PlaceInto` goal, `RobotState`, `SafetyEvent`)와 **JSON API 경계**(web↔planner, web↔브라우저)에만. 다른 메시지 안에 중첩되어서만 쓰이는 `DetectedObject`, `GraspCandidate`는 부모 메시지의 버전을 따르므로 제외 |
| `trace_id` | 명령 입력(또는 음성 녹음 시작) 시점부터 결과 반환까지 동일하게 유지 | `web`이 명령 접수 시 발급. `WorldState`, `Pick`/`PlaceInto` goal, DB 각 테이블로 전파 |
| `sequence_id` | `trace_id`의 하위 개념 — 하나의 trace 안에서 `planner`가 시퀀스를 생성하는 시점에 발급 | `task_sequences`, `execution_logs` (기존 그대로 유지) |
| `request_id` | 개별 액션 요청 식별자. 재전송 시 같은 ID를 사용해 중복 실행 방지 | `Pick`/`PlaceInto` goal. `control`이 최근 처리한 `request_id`를 짧게 캐시해 중복 실행을 실제로 막아야 한다 — 필드만으로는 방지되지 않는다 |
| `created_at` / `stamp` | JSON·DB 경계는 ISO 8601 문자열로 `created_at`, ROS2 메시지 내부는 `builtin_interfaces/Time stamp`(ROS2 관례) | 이름 충돌 방지를 위해 경계를 넘을 때만 이름을 바꾼다 |

**추적 계층 구조**: 하나의 `trace_id` 아래 하나의 `sequence_id`, 그 아래 `Pick`/`PlaceInto` 호출마다 여러 개의 `request_id`가 달린다.

```
trace_id (명령 1건)
  └─ sequence_id (그 명령에서 생성된 시퀀스 1개)
       ├─ request_id (pick 호출 1)
       ├─ request_id (place_into 호출 1)
       └─ request_id (pick 호출 2, 재시도 시에도 동일 유지)
```

### 1.1 단위 규칙 (확정)

**모든 길이는 mm로 통일한다.** 계층 경계를 넘는 값(ROS2 메시지·액션, HTTP JSON, DB, `bins.yaml`)은 예외 없이 mm다.

| 종류 | 단위 | 예 |
| --- | --- | --- |
| 길이/좌표 | **mm** | `position_base_mm`, `gripper_width_mm`, `bins.yaml`의 `pose.x` |
| 회전 | 쿼터니언(무차원). 오일러로 표기할 때만 도(deg) | `geometry_msgs/Pose.orientation` |
| 시간 | ms | `cycle_time_ms` |
| 힘 | N | `max_grip_force_n`, `contact_threshold_n` |

근거: 두산 로봇 API(`get_current_posx`)와 hand-eye 결과(`T_gripper2camera.npy`)가 모두 mm 기준이다. 계층마다 단위를 바꾸면 1000배 오차가 조용히 섞여 들어온다.

**필드 이름에 단위 접미사를 붙인다**(`_mm`/`_ms`/`_n`). 단위를 이름으로 강제하면 문서를 안 봐도 틀리기 어렵다.

**파지력은 단계 번호로 전달하고, 그 번호→힘(N) 매핑은 설정 블록이 소유한다.** 액션 goal과
`DetectedObject`는 `grip_level`(uint8 1~5)만 운반한다. 1=가장 강하게(40N) ~ 5=가장 약하게
(20N), 5N 간격이며, 값이 없거나(0) 범위 밖이면 어느 계층에서도 **5로 처리**한다.
단계→힘·속도 매핑(`grip_levels` 블록)은 `objects.yaml`과 `skill_params.yaml` 두 곳에 두고
항상 일치시킨다.

**단 하나의 예외 — ROS 표준 인터페이스**: ROS의 `geometry_msgs`는 REP-103에 따라 m가 관례이고, MoveIt2·tf2 같은 외부 표준 스택은 m로 동작한다. 따라서 `sort_msgs` 안의 `geometry_msgs/Point`·`Pose`는 **우리 규칙(mm)을 따르되**, 그런 스택에 넘기거나 받는 순간에만 m로 환산한다. 환산은 `control` 내부 한 곳(`src/control/control/units.py`)에서만 수행하며, 다른 어떤 계층도 단위를 바꾸지 않는다 — 변환 지점이 둘 이상이 되는 순간 이 규칙은 무의미해진다.

**현재 구현은 이 경계를 실제로 넘지 않는다.** 모션은 MoveIt2가 아니라 두산 드라이버의 `MovejH2r`/`MovelH2r` 액션으로 직접 내보내고, 두산 API(`get_current_posx`·`ikin`)가 이미 mm 기준이라 환산할 일이 없다. `units.py`는 그래서 지금 호출되는 곳이 없는 **경계 준비물**이다 — MoveIt2/tf2가 붙는 날 이 파일만 쓰면 되도록 남겨 둔다. 예외의 예외는 그리퍼 개폭 설정값 하나(`skill_params.yaml`의 `motion.gripper_open_m`, m 단위)로, 이 값은 메시지 경계를 넘지 않고 `control` 안에서만 쓰인다.

## 2. 토픽·액션 개요

| 이름 | 종류 | 타입 | 발행/제공 | 구독/호출 |
| --- | --- | --- | --- | --- |
| `/perception/world_state_raw` | 토픽 | `WorldState` | perception | **grasp만** (내부 릴레이 입력) |
| `/perception/instance_masks` | 토픽 | `InstanceMasks` | perception | grasp (내부용, 2절 하단 참고) |
| `/world_state` | 토픽 | `WorldState` | **grasp** | planner, web |
| `/control/robot_state` | 토픽 | `RobotState` | control | **web** |
| `/control/safety_events` | 토픽 | `SafetyEvent` | control | web, planner |
| `/control/selected_grasp` | 토픽 | `SelectedGrasp` | control | **grasp만** (디버그 오버레이 강조용, transient local QoS) |
| `/perception/debug_image` | 토픽 | `sensor_msgs/Image` | perception | 진단용(rqt 등) |
| `/grasp/debug_image` | 토픽 | `sensor_msgs/Image` | grasp | web (관측 뷰로 중계, 화면정의서 2.2.4절) |
| `pick` | 액션 | `Pick` | control | planner(경유 web) |
| `place_into` | 액션 | `PlaceInto` | control | planner(경유 web) |
| `home` | 액션 | `Home` | control | **web** (planner 미경유 — 웹_인터페이스_정의서 2.6절) |
| `observe` | 액션 | `Observe` | perception | **web** (온디맨드 관측 트리거, 2.0절 개정 · 4.4절) |

**외부 의존성**: `perception`과 `grasp`는 `realsense-ros`의 `/camera/color/image_raw`, `/camera/aligned_depth_to_color/image_raw`, `/camera/color/camera_info`를 함께 쓴다. depth는 color와 같은 픽셀 grid·camera frame의 `16UC1`(mm, `mono16` 호환)이어야 하며, `InstanceMasks`도 그 color grid·camera frame을 따른다. 이 입력을 만족할 때만 grasp가 CameraInfo K로 point cloud를 재구성한다.

### 2.0 world_state 릴레이 구조 (확정, 발행 계기 개정 — `docs/on-demand-perception.md`)

**perception은 더 이상 주기 발행하지 않는다.** 원래 이 절은 `perception`이 고정 주기
(`period_s=0.5`)로 계속 발행한다는 것을 전제했다. 온디맨드 전환 이후 `perception`은
`observe` 액션(4.4절) goal을 받았을 때만 한 번 검출하고 아래 릴레이를 태운다 — **아래
릴레이 구조 자체(두 토픽 분리, stamp로 짝짓기, 최종 발행자는 grasp 하나)는 그대로다.**
"주기적으로 오냐 vs. 트리거로 오냐"만 바뀌었을 뿐, `grasp`/`planner`/`web`이 받는 메시지
모양과 계약은 동일하다 — 그래서 `grasp` 노드는 이 전환에서 코드를 한 줄도 바꾸지 않는다.

`WorldState`는 `grasp_candidates`가 채워져야 완성되는데, 그 계산은 `grasp`가 한다. 두 노드가 같은 토픽에 동시에 발행하면 구독자가 "빈 버전"과 "완성 버전" 중 무엇을 받았는지 구분할 수 없는 경쟁 상태가 생기므로, **토픽을 분리해 최종 토픽의 발행자를 하나로 고정**한다.

```
perception ──(world_state_raw, grasp_candidates 없음)──▶ grasp ──(world_state, 완성본)──▶ planner, web
perception ──(instance_masks)──────────────────────────▶ grasp
```

`grasp`는 `world_state_raw`와 `instance_masks`를 같은 `stamp`로 매칭해 물체별 포인트클라우드를 내부에서 계산하고, `grasp_candidates`를 채운 뒤 `/world_state`로 발행한다. (매칭은 `message_filters`가 아니라 자체 대칭 dict 구조다 — 두 메시지가 `header`가 아니라 평범한 필드로 `stamp`를 갖고 있어 `message_filters`의 전제와 안 맞는다. `grasp/node.py` 모듈 docstring 참조.) **`planner`/`web`은 `world_state_raw`의 존재를 몰라도 된다** — 완성본(`/world_state`) 하나만 구독하면 그라운딩에 필요한 모든 정보(위치, 속성, 파지 후보)가 이미 들어있다.

`world_state_raw`가 `perception` 네임스페이스에 남아있는 이유는 `perception`이 여전히 그 데이터의 원 출처이기 때문이다. 반면 최종 `/world_state`는 특정 노드 소유가 아닌 **파이프라인의 산출물**이라는 의미로 네임스페이스 접두어를 붙이지 않았다.

## 3. 메시지 정의

### 3.1 GraspCandidate.msg

grasp 노드가 계산한 개별 파지 후보 하나. `DetectedObject`에 중첩되므로 `schema_version` 없음.

```
geometry_msgs/Pose pose        # base 좌표계 기준 파지 자세; position은 프로젝트 규칙의 mm
float32 score                  # 신뢰도 0.0~1.0
float32 gripper_width_mm       # 전략이 예측한 필요 그리퍼 개폭(mm). RobotState.gripper_width_mm과
                                # 같은 단위·의미(실제 대신 목표값)다. 0이면 미상(폭을 못 낸 전략) —
                                # control은 그럴 때 기본 개폭(motion.gripper_open_m)으로 대체한다.

# 이 관측에서 이 후보를 가리키는 식별값. "<object_id>#<순위>" 형식이고 순위는 0이 1순위다.
# Top-K를 그대로 내보내므로(2026-09-07) 로그·웹·planner가 같은 후보를 가리킬 방법이 필요하다.
string candidate_id

# 전략이 "무는 지점까지 얼마나 파고드는지"로 본 값(mm). GraspNet은 예측값(depth_m x 1000)을,
# heuristic_pca는 grasp_depth_mm를 넣는다. 0이면 미상. 진단·비교용이고 control은 쓰지 않는다.
float32 grasp_depth_mm

string STRATEGY_HEURISTIC_PCA=heuristic_pca
string STRATEGY_CONTACT_GRASPNET=contact_graspnet
string STRATEGY_GRASPNET_BASELINE=graspnet_baseline
string strategy                # 어떤 방법으로 이 후보를 냈는지 (3단계 비교 실험용)
```

### 3.2 DetectedObject.msg

perception이 발행하는 물체 하나. `WorldState`에 중첩되므로 `schema_version` 없음. `attributes`는 중첩 dict를 지원하지 않는 ROS2 msg 특성상 flatten해서 필드로 둔다.

```
string object_id               # 예: obj_003
string class_name               # 예: glass_bottle
string name_ko                  # 예: 유리병
float32 confidence

geometry_msgs/Point position_base_mm   # base 좌표계 3D 위치. 단위 mm (인터페이스_정의서 1.1절)

float32 depth_valid_ratio      # 낮으면 투명/반사 의심 (8단계 확장에서 활용)

# 물체가 자기 지지면(작업대 등) 위로 얼마나 솟아 있는지. depth로 실측한다 —
# position_base_mm.z(마스크 안쪽 median depth = 보이는 윗면)에서 마스크 바깥 링의
# 지지면 z를 뺀 값이다(perception/mask_utils.support_3d).
# 0이면 미상(링에 유효 depth가 없었거나 TCP 자세를 못 받은 경우).
#
# **쓰임**: place_into가 물체를 바구니에 놓을 z를 정할 때 쓴다. bin_pose는 빈 그리퍼로
# 티칭한 높이라, 큰 물체를 든 채 그 높이까지 내려가면 물체가 바닥에 먼저 닿아 로봇이
# 안전모드로 들어간다(2026-09-06 실물). 지지면 z = position_base_mm.z - height_mm 이므로
# 이 둘과 파지 z가 있으면 "물체가 TCP보다 얼마나 아래로 내려와 있는지"가 나온다.
float32 height_mm
# grasp가 object-only cloud의 XY convex hull로 채운다. base 좌표계 mm.
# 빈 polygon이면 footprint 미상이며 box boundary 검사를 활성화하지 않는다.
geometry_msgs/Polygon footprint_base_mm
bool graspable
string not_graspable_reason    # graspable=false일 때만 값 있음, 아니면 빈 문자열

# --- 속성 ---
# detector=yolo:    objects.yaml / object_attributes 테이블과 1:1 대응
# detector=vlm_sam: 사진을 본 VLM의 판단 (attr_source=llm_suggested, needs_confirmation=true)
#                   — docs/vlm_sam_pipeline.md의 [클래스 어휘를 주지 않는다]
float32 mass_g
bool fragile
bool deformable
bool transparent

# 파지력 단계: 1(매우 강하게, 40N) ~ 5(매우 약하게, 20N), 5N 간격.
# 단계→힘 매핑은 control/config/skill_params.yaml의 grip_levels 블록이 소유한다.
# 0이면 미상 — control은 5(가장 약하게)로 처리한다.
uint8 GRIP_VERY_STRONG=1
uint8 GRIP_STRONG=2
uint8 GRIP_MODERATE=3
uint8 GRIP_GENTLE=4
uint8 GRIP_VERY_GENTLE=5
uint8 grip_level

string SOURCE_YAML=yaml_seed
string SOURCE_LLM=llm_suggested
string SOURCE_USER=user_confirmed
string attr_source

bool needs_confirmation        # true면 신규 클래스, 사람 확인 대기 (5단계)

GraspCandidate[] grasp_candidates   # grasp 노드가 채워넣음. planner는 이미 채워진 것만 받음
```

**2D 바운딩박스 필드는 없다.** 세그멘테이션으로 검출 방식을 확정했으므로, 픽셀 좌표가 필요한 순간(3D 위치 계산)은 마스크(`InstanceMasks`)로 처리하고 `DetectedObject`에는 이미 계산된 결과만 남긴다.

### 3.3 InstanceMasks.msg

`perception`이 발행하고 `grasp`만 구독하는 내부용 토픽. `WorldState`와 `stamp`로 동기화해서 매칭한다. `grasp`는 이 마스크로 포인트클라우드를 자기 프로세스 안에서만 재구성하며, 그 결과를 다시 밖으로 내보내지 않는다(2.1절).

```
string schema_version
string trace_id
string observation_id          # 짝이 되는 WorldState.observation_id와 반드시 같아야 함
builtin_interfaces/Time stamp
string[] object_ids            # WorldState.objects의 object_id와 1:1 대응
sensor_msgs/Image[] masks      # object_id별 단일 채널 마스크 (mono8, 0/255)
```

### 3.4 WorldState.msg

동일한 스키마가 두 토픽에서 쓰인다 — `perception`이 `/perception/world_state_raw`로 1차 발행할 때는 `objects[].grasp_candidates`가 빈 배열이고, `grasp`가 `/world_state`로 최종 발행할 때는 채워져 있다(2.0절). `planner`/`web`은 `/world_state`만 구독하므로 항상 채워진 버전만 본다.

```
string schema_version
string trace_id
```

### 3.5 RobotState.msg

`control`이 주기적으로 발행하는 로봇 상태. 특정 명령·trace에 묶이지 않는 지속 상태라 `trace_id`는 없다.

```
# get_current_tcp가 돌려준 현재 설정된 TCP 이름 — 화면의 TCP 상태 표시용(화면정의서.md
# 2.2.2절). 좌표가 아니라 **설정 자체가 살아있는지**를 보려는 것이다: TCP(GripperDA_v1,
```

**구독자는 `web`이다 (`planner`가 아니다).** `planner`가 실시간 ROS2 스트림을 직접 구독하면 NFR-04(LLM 계획 단계는 실시간 제어 루프와 분리)가 흐려진다. `planner`가 로봇 상태를 알아야 하는 판단이 필요하면, `web`이 상태를 보고 HTTP로 `planner`에 전달한다.

### 3.6 SafetyEvent.msg

`control`이 비상정지·충돌·제한 위반 발생 시 발행한다. 특정 요청 중에 발생할 수도, 유휴 상태에서 발생할 수도 있어 `trace_id`/`aborted_request_id`는 선택값이다.

```

```

**검증기(FR-12)의 게이트 조건으로 쓴다.** 활성 안전 이벤트가 있으면 `planner`가 새 시퀀스를 생성해도 검증기가 통과시키지 않는다.

### 3.7 SelectedGrasp.msg

`control`이 **실제로 실행하기로 고른 후보 하나**를 알린다. 유일한 구독자는 `grasp`이고, 디버그 이미지에서 그 후보만 강조해 그리는 데 쓴다 — 화면이 실행과 다른 후보를 강조하면 안 되기 때문이다(후보 랭킹의 최종 결정권은 `control`에 있어 1순위가 아닐 수 있다, 4.1절).

```
string schema_version
string trace_id
string observation_id
GraspCandidate candidate
```

최신 하나만 의미가 있고 늦게 붙은 구독자도 받아야 하므로 발행·구독 양쪽 다 `depth=1`의 **transient local** QoS를 쓴다. `candidate_id`가 빈 문자열이면 "고른 것이 없다"(전 후보 탈락)는 뜻이라 강조를 지운다.

**서비스가 아니라 액션인 이유**: 2.6절은 정지를 "`mode`와 무관하게 항상 허용되는 유일한 엔드포인트"로 규정하고, 정지는 진행 중인 액션 goal을 취소하는 방식으로 구현된다. 홈이동을 서비스로 두면 **한번 시작하면 멈출 수 없는 수 초짜리 모션**이 생긴다. 인터페이스 모양을 정한 것은 관례가 아니라 이 요구다.

`trace_id`가 없는 것은 홈이동이 요청 추적 계층(1절)에 편입되지 않기 때문이고, `request_id`가 있는 것은 중복 실행 방지가 추적 계층과 무관한 전송 계층의 계약이기 때문이다. 발급자는 `web/ros_bridge.py`다 — 상위에 발급해 줄 계층이 없다.

`Pick`/`PlaceInto`와 달리 `retries_used`가 없다. 홈 자세는 재시도해서 나아질 종류의 동작이 아니다(실패하면 원인이 경로·충돌이지 파지 불확실성이 아니다).

**호출자는 web(`orchestrator._wait_for_fresh_observation`)이다.** perception이 더 이상
주기 발행하지 않으므로, `world_state_raw`/`instance_masks`가 생기려면 이 액션이 먼저
성공해야 한다 — `Home`과 마찬가지로 서비스가 아니라 액션인 이유도 같다: SAM+VLM 왕복이
수 초~10초대라 정지로 취소할 수 있어야 한다.

**두 모드**(`docs/on-demand-perception.md` D-1):
- `MODE_FULL` — 장면 전체를 SAM everything으로 조각내고 VLM에 번호별 판단을 물어 "무엇이
  있는가"를 새로 안다. 명령 접수 시·재계획 전 딱 한 번만 쓴다 — VLM 호출이 여기 한
  번뿐이라는 원칙(명령당 1회)이 여기서 지켜진다.
- `MODE_REPROMPT` — 직전 관측이 남긴 물체들이 지금 프레임에도 있는지, 재투영한 박스를
  SAM에 프롬프트로만 준다. VLM은 부르지 않는다. pick/place_into 스텝 사이처럼 자주
  불러도 되는 쪽이다.

**`object_count`/`stamp`가 있고 `retries_used`가 없다.** 관측은 재시도해서 나아질 성질의
동작이 아니다(실패하면 원인이 카메라·자세·VLM 가용성이지 파지 불확실성이 아니다) — 대신
호출자가 "몇 개를 봤는지"와 "그 결과가 어느 stamp로 나갔는지"를 바로 알아야 뒤이어
`/world_state`의 stamp 변화를 기다릴 수 있다.

**`REASON_VLM_UNAVAILABLE`은 `MODE_FULL`에서만 나온다** — `MODE_REPROMPT`는 VLM을 안
부르므로 그 경로에서는 나올 수 없다. `REASON_NOTHING_TO_REPROMPT`는 반대로 `MODE_REPROMPT`
전용이다(되돌릴 직전 관측이 없거나, 재투영한 물체가 전부 화면 밖으로 나갔을 때).

## 5. 설정 파일 스키마

### 5.1 objects.yaml

물체 속성의 유일한 소스(`src/perception/config/objects.yaml`). 예전에는 런타임에 DB `object_attributes` 테이블로 옮겨져 갱신될 계획이었으나, 그 갱신 경로(신규 물체 확인 루프, FR-05b — 확인 UI는 만들어졌지만 저장 지점 `vlm_client.py`가 TODO 스텁으로 남아 값이 채워진 적이 없다)가 끝까지 구현되지 않아 2026-09-09 테이블째 제거했다 — 지금은 이 파일이 갱신도 조회도 겸한다(시스템명세서 3.1a절).

**2026-09-08부터 `detector:=vlm_sam` 경로는 이 파일의 `objects`/`model_labels`를 읽지 않는다.** 그 경로에서는 사진을 본 VLM이 이름과 속성과 파지 단계를 함께 답하고 그대로 `DetectedObject`가 된다(`attr_source=llm_suggested`, `needs_confirmation=true`, `docs/vlm_sam_pipeline.md`의 [클래스 어휘를 주지 않는다]). `detector:=yolo`는 예전 그대로 이 표를 지난다. `grip_levels` 블록(힘·속도 실수값)은 어느 경로에서나 쓰인다 — VLM이 고르는 것은 단계 **번호(1~5)** 이고 그 번호가 가리키는 값은 여기와 `skill_params.yaml`에 있다.

```yaml

  1: { max_grip_force_n: 40.0, approach_speed: 0.25, contact_threshold_n: 8.0 }
  2: { max_grip_force_n: 35.0, approach_speed: 0.25, contact_threshold_n: 7.0 }
  3: { max_grip_force_n: 30.0, approach_speed: 0.20, contact_threshold_n: 6.0 }
```

**`model_labels`가 별도 블록인 이유**: 검출 모델의 라벨과 시스템의 `class_name`이 항상 같지는 않다(예: `dentimate_new_total_care_toothpaste` → `toothpaste`). `perception`이 모델 출력을 `DetectedObject.class_name`으로 옮길 때 이 표를 지나야 한다 — 지나지 않으면 속성 조회가 어긋나 해당 물체가 매번 미확인 신규품목이 되고 FR-05b에 따라 `grip_level 5`(가장 약하게)가 강제된다. **오류로 드러나지 않고 조용히 느려지기만 하는 종류의 어긋남**이라 표를 눈에 보이는 곳에 둔다. 이름이 같은 클래스도 함께 적어 모델 어휘 전체가 한눈에 보이게 한다.

`execution_logs.class_name`은 실행 당시 값을 자체 보존하며 어떤 속성 테이블도 FK로 참조하지 않는다(DB `object_attributes`는 2026-09-09 제거됨). 따라서 클래스를 `objects.yaml`에서 은퇴시켜도 과거 실행 이력은 유지된다 — 이미 기록된 실행 로그를 변경하지 않는다.

### 5.2 bins.yaml

분류 목적지 정의. 캘리브레이션 단계에서 실측해 고정한다. `src/control/config/bins.yaml`에 위치하며, `control`(좌표 변환)과 `planner`·`web`(그라운딩·표시)이 읽기 전용으로 공유한다.

**좌표는 mm다**(1.1절). `get_current_posx()`로 읽은 실제 TCP 자세를 그대로 적고, 회전은 쿼터니언으로 변환해 둔다.

```yaml
bins:
  left_box:
    name_ko: 왼쪽 박스
    # 티칭한 놓기 자세 (base 좌표계, mm)
    pose: { x: 334.684, y: -479.249, z: 183.820,
            qx: 0.003103, qy: 0.999995, qz: -0.000428, qw: -0.001010 }
    # --- 아래 3개가 다 있을 때만 box geometry 모드가 켜진다 (없으면 위 pose 폴백) ---
    inner_corners_base_mm:        # 상단 내부 모서리 4점. 닫힌 손끝 중앙으로 접촉해 실측
      front_left:  [385.898, -371.494, 139.609]
      front_right: [264.086, -368.680, 141.814]
      rear_right:  [256.111, -578.083, 138.101]
      rear_left:   [391.268, -569.062, 131.276]
    floor_point_base_mm: [321.596, -472.100, -5.512]   # 내부 바닥점. z만 쓴다
    wall_margin_mm: 0.0                                 # 물체 윤곽과 벽 사이 안전 여유
  right_box:
    name_ko: 오른쪽 박스
    ...
```

`inner_corners_base_mm`/`floor_point_base_mm`이 있으면 중심·폭·깊이·yaw·바닥 z를 그 5점에서 계산하므로 별도 티칭 중심점을 요구하지 않고, 물체 footprint가 그 경계 안에 들어가는지 회전 피팅까지 본다(`control/box_geometry.py`). **추정값을 넣지 않는다** — 실측하지 않았으면 아예 빼서 폴백으로 두는 편이 낫다.

## 7. 미확정 항목

- ~~**`WorldState.trace_id`를 perception이 발급할 수 없다.**~~ → **해소(온디맨드 전환).** 관측이 명령 흐름 안에서 일어나므로 web이 발급한 `trace_id`가 `Observe` goal에 실려 오고, 관측 자체를 식별하는 값은 `observation_id`(= `Observe.Goal.request_id`)로 분리했다. `WorldState`/`InstanceMasks`가 둘 다 그 값을 싣고, `Pick`/`PlaceInto` goal의 `source_observation_id`가 "어느 관측을 근거로 실행하는가"를 끝까지 물고 간다

- ~~`grasp`가 `world_state_raw`+`instance_masks` 동기화에 쓸 매칭 정책 (`ApproximateTimeSynchronizer`)~~ → **확정**: `message_filters`를 쓰지 않는다. 두 메시지가 `header`가 아니라 평범한 필드로 `stamp`를 갖고 있어 그 라이브러리의 전제와 맞지 않는다 — `grasp/node.py`가 `stamp`를 키로 하는 자체 대칭 dict로 짝을 맞춘다
- 검증기(FR-12)의 "목적지 그라운딩" 체크 로직 — `bin_id`가 `bins.yaml`에 없을 때 거부 응답의 정확한 스키마
- `InstanceMasks.masks`의 압축 여부 (원본 `sensor_msgs/Image` vs `CompressedImage`) — 네트워크 부하 실측 후 결정
- `needs_reobserve` 처리 후 능동 재촬영 결과가 기존 `object_id`를 유지하는지, 새 ID로 갱신되는지
- `RobotState`를 DB에 얼마나 자주 스냅샷할지 (매 프레임 기록은 과함, 주기 미정)
- ~~`control`이 `request_id` 중복 실행 방지를 위해 최근 처리 ID를 얼마나 오래/어떤 방식으로 보관할지~~ → **확정(B4)**: 메모리 캐시, TTL 60초·최대 256건(`control/control/request_cache.py`). 재전송은 통신 실패 직후에 일어나므로 수십 초면 충분하고, 그보다 오래된 같은 ID는 재전송이 아니라 새 요청으로 보는 편이 안전하다. 영속 저장하지 않는다
