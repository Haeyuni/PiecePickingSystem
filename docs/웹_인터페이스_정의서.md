# 인터페이스 정의서: 웹/HTTP API

`sort_msgs` 인터페이스 정의서가 ROS2 메시지·액션(perception/grasp/control 사이)을 다룬다면, 본 문서는 **ROS2가 아닌 경계** — 브라우저↔`web`, `web`↔`planner`, `perception`↔`planner` — 의 HTTP/WebSocket/JSON 계약을 정의한다.

| 항목 | 내용 |
|---|---|
| 문서 버전 | v1.1 (2.6절 로봇 직접 제어 추가) |
| 대상 | `web/web/main.py`(프론트 대면 API), `web/web/ros_bridge.py`(ROS2 경계), `planner/src/app.py` |
| 관련 문서 | `인터페이스_정의서.md`(sort_msgs), 시스템명세서 |

**경계 원칙**: `Pick`/`PlaceInto` 실행 자체(로봇 동작)는 `web/ros_bridge.py`가 ROS2 액션으로 직접 호출한다 — 이건 `sort_msgs` 문서가 정본이고 본 문서에서 중복하지 않는다. 본 문서는 그 앞뒤, 즉 "명령이 어떻게 들어오고 결과가 어떻게 화면에 보이는가"만 다룬다.

**공통 필드**: `schema_version`/`trace_id`/`sequence_id`/`request_id`는 `인터페이스_정의서.md` 1절의 규칙을 그대로 따른다. JSON 경계이므로 시간 필드는 항상 `created_at`(ISO 8601)을 쓴다(`stamp`는 ROS2 내부 전용).

---

## 1. 전체 흐름 개요

```
[브라우저]
   │ POST /api/stt (음성만, 2차)         │ POST /api/commands (텍스트)
   ▼                                      ▼
[web/main.py] ──HTTP──▶ [planner/app.py] ──(검증 통과 시)──▶ [web/ros_bridge.py] ──ROS2 액션──▶ [control]
   ▲                                      │
   │ WebSocket (실시간 푸시)                │ HTTP (신규 물체 발견 시, perception이 직접 호출)
   │                              [perception] ──POST /internal/object-suggestions──▶ [planner/app.py]
   │
   └── robot_state, safety_events, 실행 진행상황을 web/ros_bridge.py가 ROS2에서 받아 WebSocket으로 중계

[브라우저] ── POST /api/robot/stop, /api/robot/home ──▶ [web/ros_bridge.py] ──ROS2──▶ [control]
   (planner를 거치지 않음 — 2.6절)
```

**승인 절차 없음**: 검증기를 통과한 시퀀스는 자동 실행된다(이전 결정 반영). 브라우저는 진행 상황을 실시간으로 볼 뿐, 실행을 막는 승인 버튼은 없다. 단, 신규 물체 확인(FR-05b)은 별개로 유지된다 — 이건 승인이 아니라 "속성 확정"이다.

**결정적 로봇 동작은 LLM 파이프라인을 거치지 않는다**: 정지·홈이동처럼 자연어 해석이나 그라운딩이 필요 없는 동작은 `/api/commands`(→`planner`)가 아니라 별도 경로(2.6절)로 `control`에 직접 도달한다. 특히 정지는 로봇이 `busy`일 때 가장 필요한 동작이라, 2.1절의 "busy면 거부" 규칙과 무관하게 항상 허용된다.

## 2. 브라우저 ↔ web

### 2.1 명령 입력

**`POST /api/commands`**

`web`은 `planner`를 호출하기 전, 현재 `robot_state.mode`(4절 WebSocket으로 이미 받아 보유 중)를 확인한다. `busy`/`error`/`estopped`면 즉시 거부하고 `planner`를 호출하지 않는다 — 실시간 로봇 상태를 모르는 `planner`가 아니라 `web`이 이 판단을 맡는다(NFR-04와 동일 원칙, `RobotState` 구독자가 `web`인 이유).

```json
// 409 Conflict — mode: busy
{ "schema_version": "1.0.0",
  "error": { "code": "ROBOT_BUSY", "message": "로봇이 이전 명령을 처리 중입니다" } }

// 409 Conflict — mode: estopped
{ "schema_version": "1.0.0",
  "error": { "code": "ROBOT_ESTOPPED", "message": "비상정지 상태입니다. 수동 리셋이 필요합니다" } }
```

프론트엔드는 `robot_state.mode !== 'idle'`일 때 명령 입력창을 비활성화해 즉각적인 피드백을 주지만, 이건 UX 차원의 보조 수단이다. **실제 차단은 항상 `web` 백엔드가 한다** — 여러 탭이나 개발자도구 우회로 UI 차단을 건너뛰어도 백엔드에서 막힌다.

```json
// Request
{
  "schema_version": "1.0.0",
  "command_text": "깨지기 쉬운 것만 왼쪽 박스로 옮겨줘"
}

// Response 202 Accepted
{
  "schema_version": "1.0.0",
  "trace_id": "tr-8f3a...",     // web이 여기서 발급
  "status": "processing"
}
```

이후 진행 상황은 폴링이 아니라 **WebSocket**(4절)으로 받는 게 기본이다. `GET /api/traces/{trace_id}`(아래)는 새로고침·재접속 시의 폴백이다.

### 2.2 음성 명령 (2차, 6단계)

**`POST /api/stt`** — 실행하지 않는다. 텍스트로 바꿔서 돌려줄 뿐이다(FR-24: 확인·수정 후 실행).

```
Request: multipart/form-data, 필드명 "audio" (webm/wav)

Response 200
{
  "schema_version": "1.0.0",
  "recognized_text": "깨지기 쉬운 것만 왼쪽 박스로 옮겨줘",
  "confidence": 0.93,
  "low_confidence": false     // confidence < 0.8이면 true. FR-25에 따라 재입력 유도, command_text로 자동 전달 금지
}
```

브라우저는 이 결과를 화면에 보여주고, 사용자가 확인(또는 수정) 후 **2.1절의 `/api/commands`를 그대로 호출**한다. STT 전용 실행 경로는 없다(FR-23).

### 2.3 시퀀스/실행 상태 조회 (폴백)

**`GET /api/traces/{trace_id}`**

```json
{
  "schema_version": "1.0.0",
  "trace_id": "tr-8f3a...",
  "command_text": "깨지기 쉬운 것만 왼쪽 박스로 옮겨줘",
  "validation_status": "approved",   // approved | rejected
  "validation_reason": null,
  "sequence_id": "sq-1c02...",
  "steps": [
    { "request_id": "rq-01", "skill": "pick", "object_id": "obj_001",
      "status": "success", "phase": "verifying" },
    { "request_id": "rq-02", "skill": "place_into", "object_id": "obj_001",
      "status": "in_progress", "phase": "moving" }
  ]
}
```

### 2.4 신규 물체 확인 (FR-05b)

**`GET /api/object-confirmations`** — 확인 대기 목록.

```json
{
  "schema_version": "1.0.0",
  "items": [
    {
      "class_name": "unknown_003",
      "suggested_name_ko": "유리병",
      "suggested_mass_g": 380,
      "suggested_fragile": true,
      "suggested_deformable": false,
      "suggested_transparent": true,
      "suggested_by_model": "<VLM 모델 ID 문자열 그대로>",
      "image_ref": "data/unknown_crops/unknown_003.png",
      "created_at": "2026-09-03T05:11:00Z"
    }
  ]
}
```

**`POST /api/object-confirmations/{class_name}`** — 승인 또는 수정.

```json
// Request (그대로 승인)
{ "schema_version": "1.0.0", "approved": true }

// Request (수정 후 승인 — 예: VLM이 놓친 부분 정정)
{ "schema_version": "1.0.0", "approved": true,
  "corrections": { "fragile": false, "profile": "normal" } }

// Response 200
{ "schema_version": "1.0.0", "class_name": "unknown_003", "is_confirmed": true }
```

승인 즉시 `object_attributes.source='user_confirmed'`, `is_confirmed=true`로 갱신된다(3.1a절). **이 확인이 없는 한 해당 클래스는 계속 `fallback` 프로파일로만 시도된다** — NFR-03a 그대로 유지.

### 2.5 실행 이력 조회 (대시보드용)

**`GET /api/executions?trace_id=...&limit=50`** — `execution_logs`를 그대로 노출. web이 DB에 직접 접근하므로 planner를 거치지 않는다.

### 2.6 로봇 직접 제어 (LLM 미경유)

자연어 해석·그라운딩이 필요 없는 결정적 동작. `web/main.py`가 `planner`를 거치지 않고 `web/ros_bridge.py`를 통해 곧바로 `control`에 도달한다.

**`POST /api/robot/stop`**

`robot_state.mode`와 **무관하게 항상 허용된다** — busy일 때 가장 필요한 동작이므로 2.1절의 차단 규칙이 적용되지 않는 유일한 엔드포인트다. `control`의 현재 액션 goal(진행 중인 `Pick`/`PlaceInto`)을 취소한다.

```json
// Response 200
{ "schema_version": "1.0.0", "stopped": true, "cancelled_request_id": "rq-01" }  // 취소된 요청 없으면 null
```

**`POST /api/robot/home`**

`mode`가 `idle`일 때만 허용된다(동작 중 홈이동은 위험하므로 `/api/commands`와 동일한 차단 규칙, 2.1절).

```json
// Response 202
{ "schema_version": "1.0.0", "status": "moving_home" }

// mode가 idle이 아니면 409 (2.1절과 동일 에러 형식)
```

두 엔드포인트 모두 `trace_id`/`sequence_id`를 발급하지 않는다 — LLM 계획 대상이 아니므로 요청 추적 계층(1절)에 편입되지 않는, 로봇 제어박스에 보내는 단발 명령이다. 다만 `execution_logs`에는 `skill_name`을 `"stop"`/`"home"`으로 남겨 이력에는 노출한다(별도 문서 `화면_정의서.md`의 이력 화면 참조).

### 2.7 최신 월드 상태 조회 (폴백)

**`GET /api/world-state`**

`WorldState`를 그대로 반환한다(`인터페이스_정의서.md` 3.2절 구조를 JSON 직렬화). 화면정의서 2.2.5절의 탐지 물체 목록이 최초 렌더에서 채워지려면 필요하다 — WebSocket은 변화가 있을 때만 밀어주므로, 새로고침 직후처럼 아무 이벤트도 오지 않는 순간에는 목록이 비어 보인다. `GET /api/traces/{trace_id}`가 실행 상태의 폴백인 것과 같은 역할이다.

아직 월드 상태를 받지 못했으면 503과 `NO_WORLD_STATE`를 반환한다(perception 미기동 등).

## 3. web ↔ planner (내부)

브라우저에는 노출되지 않는, `web`이 `planner`를 호출하는 경계다.

**`POST /internal/plan`**

```json
// Request — web이 ros_bridge에서 최신 world_state를 가져와 함께 보낸다
{
  "schema_version": "1.0.0",
  "trace_id": "tr-8f3a...",
  "command_text": "깨지기 쉬운 것만 왼쪽 박스로 옮겨줘",
  "world_state": { "...": "WorldState.msg와 동일 구조를 JSON으로 직렬화" }
}

// Response
{
  "schema_version": "1.0.0",
  "trace_id": "tr-8f3a...",
  "sequence_id": "sq-1c02...",
  "validation_status": "approved",   // approved | rejected
  "validation_reason": null,          // rejected일 때만 값 있음
  "steps": [
    { "skill": "pick", "object_id": "obj_001", "profile": "fragile",
      "grasp_pose": { "...": "geometry_msgs/Pose와 동일 구조" } },
    { "skill": "place_into", "object_id": "obj_001", "profile": "fragile",
      "bin_id": "left_box" }
  ]
}
```

`validation_status: "rejected"`면 `web`은 `ros_bridge`를 호출하지 않는다 — 로봇은 움직이지 않는다.

**재계획**: `Pick`/`PlaceInto` 실패 시, `web`이 같은 `/internal/plan`을 실패 사유와 함께 다시 호출한다(같은 `trace_id`, 새 `sequence_id`).

```json
{
  "schema_version": "1.0.0",
  "trace_id": "tr-8f3a...",
  "command_text": "깨지기 쉬운 것만 왼쪽 박스로 옮겨줘",
  "world_state": { "...": "..." },
  "previous_failure": {
    "sequence_id": "sq-1c02...",
    "request_id": "rq-01",
    "object_id": "obj_001",
    "failure_reason": "grasp_failed"
  }
}
```

## 4. WebSocket (web → 브라우저)

**`/ws/live`** — 브라우저는 연결 후 별도 구독 요청 없이 아래 이벤트를 전부 받는다(단일 채널, 이벤트 타입으로 구분).

```json
// 실행 진행상황 (Pick/PlaceInto Feedback을 그대로 중계)
{ "type": "execution_progress", "trace_id": "tr-8f3a...", "request_id": "rq-01",
  "skill": "pick", "phase": "contact_detected" }

// 실행 결과
{ "type": "execution_result", "trace_id": "tr-8f3a...", "request_id": "rq-01",
  "success": true, "failure_reason": "none" }

// 로봇 상태 (RobotState.msg 변경 시)
{ "type": "robot_state", "mode": "busy", "current_skill": "pick",
  "gripper_width_mm": 42.0 }

// 안전 이벤트 (SafetyEvent.msg 발행 시 — 지연 없이 즉시 푸시)
{ "type": "safety_event", "event_type": "e_stop", "severity": "critical",
  "description": "비상정지 버튼 눌림", "requires_manual_reset": true }

// 신규 물체 확인 대기 발생
{ "type": "object_confirmation_needed", "class_name": "unknown_003" }
```

**`safety_event`는 다른 이벤트보다 우선 처리한다** — 브라우저 UI가 이 타입을 받으면 즉시 눈에 띄게 표시해야 한다(안전 정보를 다른 알림과 같은 우선순위로 큐잉하지 않는다).

**재연결 시 이벤트 재전송 큐는 두지 않는다.** 연결이 끊겼다 다시 붙으면, 브라우저는 `GET /api/traces/{trace_id}`(2.3절)로 현재 스냅샷을 다시 받는 것으로 충분하다 — 놓친 개별 이벤트를 순서대로 재생할 필요는 없다(1차 범위, 단일 사용자 가정과 일관).

## 5. perception ↔ planner (신규 물체 발견 알림)

`perception`은 ROS2 노드지만, `planner`가 ROS2를 모르므로 이 알림은 HTTP다. `perception` 프로세스 안에 이 호출을 위한 간단한 HTTP 클라이언트가 필요하다(ROS2 노드 코드와는 별개 함수).

**`POST /internal/object-suggestions`**

```json
// Request (perception → planner)
{
  "schema_version": "1.0.0",
  "class_name": "unknown_003",
  "image_ref": "data/unknown_crops/unknown_003.png"
}

// Response 202
{ "schema_version": "1.0.0", "accepted": true }
```

`planner`가 이 요청을 받으면 즉시 응답하고, VLM 호출(3.1a절)은 비동기로 처리한다 — `perception`이 VLM 응답을 기다리며 블로킹되지 않는다. VLM 결과가 나오면 `planner`가 DB에 기록하고, `web`에는 WebSocket으로 `object_confirmation_needed`가 전파된다(4절).

**재시도 정책**: 이 알림이 실패해도 물체는 이미 `needs_confirmation=true`+`fallback` 프로파일로 안전하게 처리되고 있으므로(3.1a절), 공격적으로 재시도할 이유가 없다. 최초 시도 포함 **최대 2회**(고정 지연 2초)만 시도하고, 최종 실패 시 로그만 남기고 `perception`의 다음 프레임 처리를 막지 않는다. 같은 클래스가 다음 프레임에서도 계속 미확인 상태로 검출되면 자연스럽게 다시 알림이 시도되므로, 별도의 재시도 큐나 영속 저장은 두지 않는다.

**동일 클래스 중복 알림 방지**: `perception`은 이미 `needs_confirmation=true`로 알고 있는 클래스를 재알림하지 않는다(FR-05c와 동일 원칙 — `perception`도 마지막 `world_state_raw`에서 받은 속성 상태를 캐시로 들고 있어야 한다).

## 6. 에러 응답 형식 (공통)

모든 HTTP 엔드포인트는 실패 시 동일한 형식을 쓴다.

```json
// 4xx/5xx
{
  "schema_version": "1.0.0",
  "trace_id": "tr-8f3a...",   // 있으면 포함, 없으면 생략
  "error": { "code": "OBJECT_NOT_GROUNDED", "message": "obj_099는 현재 인지된 물체 목록에 없습니다" }
}
```

| HTTP 상태 | 상황 |
|---|---|
| 400 | 요청 스키마 오류 |
| 404 | `trace_id`/`class_name` 등 리소스 없음 |
| 409 | 로봇이 `busy`/`estopped` 상태라 새 명령 거부 (2.1절), 이미 확인된 `object-confirmation`을 다시 확인하려는 경우 등 상태 충돌 |
| 422 | 검증기 거부(그라운딩 실패, 가반하중 초과 등) — `validation_status: rejected`와 같은 정보를 HTTP 레벨에서도 노출 |
| 503 | `control`/`planner` 등 하위 서비스 응답 없음 |

## 7. 설계 원칙 요약

| 원칙 | 반영 위치 |
|---|---|
| ROS2 액션 실행은 이 문서가 아니라 `sort_msgs` 문서가 정본 | 1절 경계 원칙 |
| STT는 텍스트 변환만, 실행 경로는 텍스트 명령과 동일 | 2.2절, FR-23 |
| 실시간 상태는 폴링이 아니라 WebSocket으로 푸시 | 4절, `GET /api/traces`는 폴백 전용 |
| 안전 이벤트는 다른 알림보다 우선 처리 | 4절 `safety_event` |
| 신규 물체 미확인 시 `fallback` 프로파일 강제 (변경 없음) | 2.4절, NFR-03a |
| `perception`→`planner` 알림은 비동기, VLM 응답을 기다리며 블로킹하지 않음 | 5절 |
| 검증 실패는 실행 자체를 막음(HTTP 레벨에서도 422로 노출) | 3절, 6절 |
| 로봇 동작 중(busy/estopped)에는 새 명령을 web 백엔드가 차단, UI 비활성화는 보조 수단일 뿐 | 2.1절, `RobotState` 구독자가 web인 이유(NFR-04)와 동일 원칙 |
| perception→planner 알림 실패는 시스템 안전에 영향 없으므로 재시도는 가볍게(최대 2회), 다음 프레임이 자연스럽게 재시도를 대체 | 5절 |
| 결정적 로봇 동작(정지·홈이동)은 LLM 파이프라인을 거치지 않음. 정지는 busy 차단 규칙의 유일한 예외로 항상 허용 | 2.6절 |

## 8. 미확정 항목

- **`/internal/plan`의 안전 이벤트 전달 (3절 갱신 필요)**: FR-12는 활성 `SafetyEvent`를 검증기의 게이트 조건으로 요구하지만, `planner`는 ROS2를 모르므로 스스로 `/control/safety_events`를 구독할 수 없다. `RobotState`와 같은 이유로 이 정보의 보유자는 `web`이다. `planner`는 요청의 `active_safety_events`(`SafetyEvent` JSON 배열, 기본 빈 배열) 필드를 받도록 이미 구현되어 있으며, `web`이 이 값을 채워 보내는 시점에 3절 스키마에 정식으로 추가한다. 2.1절의 `mode` 차단(estopped/error)이 실질적으로 같은 역할을 하므로 1차 범위에서는 중복 방어에 가깝다.

- **다중 탭/세션**: 1차 범위는 단일 사용자를 가정한다(명시적으로 확정). 다만 로봇 동작 중 요청 차단(2.1절)이 `web` 백엔드에서 이루어지므로, 여러 탭이 열려 있어도 최소한 "동작 중 중복 명령"은 막힌다. 향후 다중 사용자를 지원하게 되면 `/ws/live` 세션 구분과 명령 소유권(누가 보낸 명령인지) 개념이 새로 필요하다.
- `RobotState`를 `web`이 폴링이 아니라 WebSocket으로 받는다는 전제(4절)가 실제 `ros_bridge.py` 구현에서 지연 없이 지켜지는지 — 2.1절의 busy 판단이 오래된 상태값에 의존하면 오탐이 생길 수 있어 실측 필요
