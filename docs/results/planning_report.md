`eval-v3`는 D-7(대상 물체 클래스 확정) 해소에 맞춰 평가셋의 물체를 실제 검출 클래스 `suncream`/`nail`/`tape`로 옮긴 판이다. 세 클래스가 모두 파손위험·변형 없음이라 속성 기반 선택의 축이 `fragile`에서 `transparent`(테이프만 해당)로 바뀌었고, "속성 조건에 맞는 물체가 하나도 없는" 케이스가 하나 늘었다.

**지표 정의**

- **명령 정확도** — 수행되어야 하는 지시(13건) 중, 기대한 시퀀스를 정확히 만든 비율. "승인했는가"가 아니라 **집은 물체 집합·목적지·프로파일이 전부 기대와 일치하는가**로 채점한다. 승인만 보면 엉뚱한 물체를 옮기는 계획도 통과한다.
- **거부 정확도** — 거부되어야 하는 지시(`eval-v3` 기준 9건) 중 실제로 거부한 비율.

## 2. 평가셋 구성

계획서가 요구한 5개 카테고리에, **지시 표현별 분할**을 더했다. B2의 E2E가 잡아낸 결함("전부 옮겨줘"에서 유리병이 조용히 누락)이 시나리오가 아니라 **지시어** 때문에 생겼기 때문이다 — 픽스처만 나누면 같은 종류의 결함을 또 놓친다.

| 표현 축 | 케이스 |
|---|---|
| 단일 대상 명시 | "선크림을 왼쪽 박스에 넣어줘" / "네일을 오른쪽 박스에 넣어줘" |
| 복수 대상 열거 | "테이프랑 네일을 왼쪽 박스에 넣어줘" |
| 전량 지시 | "전부" / "모두" / "다 왼쪽으로 옮겨"(구어, '박스' 생략) |
| 속성 기반 | "투명한 것만" / "투명하지 않은 것들은"(부정형) / "깨지기 쉬운 것만"(해당 물체 없음 → 거부) |
| 지시대명사 | "그거 좀 치워줘" / "그거 좀 왼쪽 박스에"(후보가 하나뿐) |
| 목적지 모호 | "저기에 넣어줘" / "적당히 정리해줘" |

세 클래스가 모두 파손위험·변형 없음이라 `fragile`·`deformable` 프로파일에 대응하는 실물이 없다. 그 경로는 **미확인 신규 클래스**가 계속 덮는다 — FR-05b가 `fragile`을 강제하므로 `unknown-class-all` 케이스가 그 자리를 지킨다. `deformable`은 지금 실물이 없고, 클래스가 늘어날 때 되살아난다.

각 행은 `world_state` 픽스처를 참조하고 기대 결과를 구조로 적는다(`pick_objects`, `bins`, `profiles`, `pick_objects_exclude`). 채점기는 기대 키를 화이트리스트로 막아, 오타가 조용히 "검사 안 함"이 되지 않게 한다.

픽스처 2종을 새로 만들었다 — 가반하중 초과와 작업반경 밖은 기존 5종에 없는 조건이었다(`world_state_overweight.json`, `world_state_out_of_workspace.json`).

## 3. 평가셋이 잡아낸 결함 (plan-v3 → plan-v4)

두 건 모두 **모호한 지시를 추측으로 실행**한 경우다. 거부했어야 할 것을 승인했으므로, 로봇이 실제로 움직였을 것이다.

| 케이스 | plan-v3의 동작 |
|---|---|
| "그거 좀 치워줘" | 3개 **전부**를 왼쪽 박스로 옮기는 계획을 승인 |
| "유리병 좀 저기에 넣어줘" | 목적지를 **임의로** 오른쪽 박스로 정해 승인 |

첫 번째는 이전 수정의 부작용으로 보인다. B2에서 "전부 지시에서 물체가 누락되는" 결함을 고치려고 규칙 6-1("전부/모두/다 지시에서는 하나도 빠뜨리지 않는다")을 넣었는데, 그 압력이 **대상이 불분명할 때도 전부를 고르는 쪽**으로 새어 나왔다. 한쪽 결함을 고친 프롬프트 규칙이 반대쪽 결함을 만든 것이고, 평가셋 없이는 보이지 않는 종류다.

**plan-v4에서 추가한 규칙**

- 7-1: 모호함을 "전부"로 넓혀서 해결하지 않는다. 지시대명사만 있어 대상을 특정할 수 없으면 거부한다. 6-1은 사용자가 실제로 "전부/모두/다"라고 말했을 때만 적용된다.
- 7-2: 목적지도 같은 기준이다. "저기"·"적당한 곳"처럼 특정할 수 없으면 목록에서 임의로 고르지 않는다. 대상이 분명해도 목적지가 모호하면 거부다.

규칙을 넣기 전에 **반대 방향의 케이스를 먼저 추가**했다(`ambiguous-pronoun-single-object`). 검출된 물체가 하나뿐이면 "그거"는 모호하지 않으므로 승인되어야 한다 — 모호함 규칙을 강화하다가 과하게 거부하는 쪽으로 넘어가는 것을 잡기 위한 케이스다. plan-v4에서 이 케이스는 계속 승인된다.

plan-v4의 거부 사유는 작업자가 무엇을 고쳐 말해야 할지 알 수 있는 형태로 나온다:

> "어떤 물체를 치워야 하는지 명확하지 않습니다. '유리병', '캔', '종이컵' 중에서 구체적으로 지시해 주세요."
> "목적지가 '저기'로 모호합니다. '왼쪽 박스'나 '오른쪽 박스' 중 하나를 지정해 주세요."

## 4. `temperature=0`은 재현을 보장하지 않는다

가반하중 초과 픽스처에 "전부 왼쪽 박스로 옮겨줘"를 넣으면 **같은 입력에 결과가 갈린다.**

| 실행 | 결과 |
|---|---|
| `eval-v2` / `plan-v4` 전체 실행 | 승인 — 물통을 빼고 나머지만 옮기는 부분 계획 |
| `eval-v3` / `plan-v4` 전체 실행 | 거부 — 물통이 시퀀스에 들어가 검증기가 막음 |
| 단일 케이스 3회 반복 | 승인 2회 / 거부 1회 |

`temperature=0`이고 프롬프트도 픽스처도 같은데 갈린다. **`temperature=0`은 결정적 출력을 보장하지 않는다** — 계획서와 이 문서의 이전 판이 재현성을 근거로 삼았던 부분은 그만큼 약하게 읽어야 한다. 같은 버전을 다시 돌려 같은 점수가 나온 것은 사실이지만, 그것이 케이스마다 항상 같은 출력이 난다는 뜻은 아니다.

갈리는 이유는 **가반하중 규칙이 프롬프트에 없기 때문**이다. 무게는 물체 요약에 들어가지만(`grounding.describe_for_prompt`) "5000g을 넘으면 빼라"는 규칙은 없다. LLM이 7200g을 보고 알아서 빼는 것은 규칙 준수가 아니라 경향이고, 경향은 실행마다 흔들린다.

작업반경 쪽은 흔들리지 않는다. 좌표를 아예 주지 않으므로(LLM이 좌표를 지어낼 여지를 없애려는 의도적 선택) LLM은 늘 도달 불가 물체를 포함시키고, 검증기가 매번 막는다.

**이 관찰이 뒷받침하는 것 두 가지**

1. **검증기가 유일한 보증이다.** 프로젝트가 처음부터 세운 원칙("검증기는 LLM 프롬프트를 신뢰하지 않는다")이 여기서 그대로 확인된다. 가반하중·작업반경 어느 쪽도 LLM의 협조에 기대지 않는다.
2. **불가능 케이스를 상태가 아니라 불변식으로 채점한 것이 옳았다.** "불가능한 물체가 승인된 계획에 들어 있지 않다"로 채점했기 때문에 두 결과 모두 통과한다. 승인/거부로 기대를 적었다면 이 케이스는 실행마다 결과가 뒤집히는 불안정한 케이스가 됐을 것이다.

**남는 문제**: 도달 불가 물체 하나 때문에 나머지가 통째로 막힌다(검증기에 부분 거부가 없다). 대응 방향은 검증기가 거부 대신 해당 물체의 pick/place 쌍을 떨어뜨리고 사유를 함께 반환하게 하거나, 도달 가능 여부를 프롬프트 요약에 불린으로 넣는 것이다. 후자가 "좌표는 LLM에 주지 않는다"는 기존 원칙을 깨지 않는다. 어느 쪽이든 이번 범위 밖이다.

## 5. 한계

이 수치를 읽을 때 함께 봐야 하는 것들이다.

1. **plan-v4의 100%는 held-out 점수가 아니다.** 실패한 두 케이스를 보고 규칙 7-1·7-2를 썼으므로, 그 두 케이스에 대해서는 평가셋에 맞춰 고친 것이다. 방어 장치로 반대 방향 케이스를 넣었지만(3절), 프롬프트를 또 고칠 때는 **새 케이스를 먼저 추가하고 나서** 고치는 순서를 지켜야 한다.
2. **22케이스는 작고, 1회 측정이다.** 카테고리당 2~10건이라 한 건이 틀리면 그 카테고리 점수가 크게 흔들린다. 게다가 4절이 보였듯 같은 케이스가 실행마다 갈릴 수 있으므로, **100%는 "한 번 돌렸을 때 전부 맞았다"는 뜻이지 "항상 맞는다"는 뜻이 아니다.** 안정성까지 주장하려면 같은 평가셋을 n회 반복해 케이스별 통과율을 내야 한다(현재 채점기는 1회 실행만 지원한다). BR 3.1절의 "100회 시행" 규모는 실물 결합(M5) 이후 분류 정확도 측정에서 채워질 몫이고, 여기서 재는 것은 계획 계층이다.
3. **속성 다양성이 줄었다.** 확정된 3종은 모두 파손위험·변형 없음이라, 실물 기준으로 구분되는 속성은 `transparent`(테이프)뿐이다. 속성 기반 선택 케이스가 사실상 한 축에만 걸려 있고, `deformable` 프로파일은 대응하는 실물이 없다. 클래스가 늘어나면 그때 축을 다시 넓혀야 한다.

   또한 `nail`의 **모델 라벨은 `nail_product`**다. `objects.yaml`의 `model_labels` 표를 perception이 실제로 지나는지는 아직 검증되지 않았다 — `node.py`가 스텁이라 검증할 코드가 없다. 이 매핑이 빠지면 네일이 매번 미확인 신규품목으로 떨어져 `fragile` 프로파일이 강제되는데, **오류로 보이지 않고 느려지기만 한다.** M5에서 가장 먼저 확인할 항목이다.
4. **파지·이송·배치의 성공 여부는 포함하지 않는다.** 여기서 재는 것은 "지시를 올바른 스킬 시퀀스로 옮겼는가"까지다. 실행 성공률(BR 3.1절 파지 성공률)은 실물 로봇이 필요하다.
5. **mock `WorldState`는 이상적이다.** `depth_valid_ratio`나 `confidence`가 낮은 경계 사례, 같은 클래스가 여러 개 있어 "네일"이 둘을 가리키는 경우가 평가셋에 없다. 후자는 지금 구조로 바로 추가할 수 있고, 3종뿐인 어휘에서는 오히려 흔한 상황이라 우선순위가 높다.

6. **가반하중·작업반경 픽스처의 큰 물체는 합성이다.** `water_jug`(7200g)와 `tool_case`(958mm)는 검출 어휘에 없다 — 실제 3종은 전부 가볍고 작업반경 안에 있어 이 한계를 시험할 물체가 없기 때문이다. 검증기의 수치 경계를 확인하는 것이 목적이므로 합성으로 두었고, `data/mock/README.md`에 표시했다.

## 6. 재현 방법

```bash
docker compose up -d db planner
docker compose exec planner python eval/run_eval.py             # 전체 실행 + eval_runs 기록
docker compose exec planner python eval/run_eval.py --dry-run   # LLM 호출 없이 평가셋만 검사
```

`--dry-run`은 채점 전에 평가셋 자체를 검사한다(픽스처 존재, 기대 키 오타, 기대 물체가 픽스처에 실제로 있는지, 승인 케이스가 내용 검사를 하나라도 하는지). 틀린 평가셋으로 낸 점수는 의미가 없으므로 채점보다 먼저 돌아간다.

프롬프트 버전이 바뀌지 않았다면 다시 돌릴 이유가 없다 — 케이스마다 LLM을 한 번씩 호출하므로 API 비용이 든다(개발계획 7절). 버전별 점수는 `eval_runs`/`eval_results`에 남아 있다.
