## 2. 개발 순서 재조정 (핵심 결정)

BR 로드맵의 숫자 순서(1단계 검출 → 2 세그멘테이션 → 3 파지 → 4 LLM)를 그대로 따르지 않고, **web·planner 계층을 먼저 개발**한다.

**근거**

1. 검출 모델 선정·학습은 현재 **Colab에서 병렬 진행 중**이다. 워크스테이션 트랙이 그 결과를 기다리며 놀 이유가 없다.
2. `WorldState`·HTTP API·화면 구성이 **이미 문서로 확정**되어 있다. 즉 perception의 실제 출력이 없어도, 같은 스키마의 mock 데이터로 상위 계층 전체를 개발·검증할 수 있다.
3. BR 7절 제약("실물 로봇 실험 시간이 제한적이므로 로봇 없이 검증 가능한 작업을 최대화한다")과 정확히 같은 방향이다.
4. web·planner는 GPU를 쓰지 않는다. Colab 학습과 워크스테이션 개발이 자원 경합 없이 동시에 돌아간다.

**단계 번호와의 매핑**: 여기서 먼저 만드는 것은 실질적으로 **4단계(LLM 지시 기반 분류)의 계획·검증·웹 부분**이다. 1~3단계(검출·세그멘테이션·파지)가 완성되면 mock 어댑터를 실제 `/world_state` 구독으로 교체하는 것으로 결합한다. 이 교체가 한 지점에서만 일어나도록 만드는 것이 트랙 B의 설계 목표다(4.2절 B2).

### 2.1 트랙 구성

| 트랙 | 장소 | 내용 | 의존성 |
|---|---|---|---|
| A | Colab | 검출 모델 선정·학습 (1~2단계) | 없음 (진행 중) |
| B | 워크스테이션 | **planner + web + DB (우선 개발)** | 없음 — mock으로 독립 진행 |
| C | 로봇 셀 | 0단계 잔여 산출물 | 로봇 접근 시간 |

세 트랙은 병렬이며, 합류 지점은 6절 마일스톤 M5다.

## 4. 트랙 B: planner + web (우선 개발)

### 4.1 원칙

- **mock은 별도 코드 경로가 아니라 어댑터 교체다.** `web`이 `ros_bridge`를 부르는 인터페이스를 먼저 고정하고, 실제 구현과 mock 구현이 같은 시그니처를 갖게 한다. STT를 별도 실행 경로로 만들지 않는 FR-23과 같은 원칙이다.
- **검증기는 LLM 프롬프트를 신뢰하지 않는다.** 그라운딩(FR-11)은 프롬프트로 유도하되, 최종 판정은 코드(`validator.py`)가 한다.
- 각 단계는 그 자체로 검증 가능한 산출물을 남긴다(BR 8절 리스크 대응 — 어느 지점에서 멈춰도 제출 가능).

### 4.2 작업 순서

#### B0. 개발 기반 (선행) — ✅ 완료 (2026-09-03)

| 작업 | 파일 | 완료 기준 | 결과 |
|---|---|---|---|
| DB 스키마 마이그레이션 | `db/migrations/001_init.sql` | 시스템명세서 2.2절 7개 테이블 생성. `grasp_strategy`·`profile`·`source`·`skill_name`·`failure_reason`은 `sort_msgs` 상수와 동일 값만 허용(CHECK) | ✅ 8개 테이블(+`schema_migrations`). 잘못된 값 3종이 CHECK로 거부되는 것 확인 |
| compose 기동 | `.env.example`, `docker-compose.yml`, `planner/Dockerfile` | `docker compose up db planner`가 뜨고 `/health` 200 | ✅ `{"status":"ok","db":"ok","object_attributes":3}` |
| `objects.yaml` → DB 시드 | `planner/src/seed.py`, `planner/src/db.py` | 최초 기동 시 `source='yaml_seed'`로 적재, 재기동 시 중복 삽입 없음 | ✅ 최초 3개 적재, 재기동 시 `{"migrations":[],"seeded":0}` |
| mock 월드 상태 픽스처 | `data/mock/world_state_*.json` | 5종: ①정상 다물체 ②신규 클래스 ③지시 대상 미검출 ④`graspable=false` ⑤빈 목록 | ✅ 5종 + `scripts/validate_mock_fixtures.py`로 `.msg` 대조 검사 |

**B0에서 내린 결정**

- **마이그레이션은 planner 기동 시 적용한다**(`db.py`). 파일이 몇 개 안 되고 planner가 DB를 쓰는 주 서비스라, 별도 마이그레이션 도구를 두는 비용이 이득보다 크다. 적용 이력은 `schema_migrations`에 남는다.
- **스키마·시드는 이미지에 굽지 않고 읽기 전용 마운트**한다(`/migrations`, `/config/objects.yaml`). 스키마를 고치려고 이미지를 재빌드할 이유가 없다.
- **시드는 기존 행을 덮어쓰지 않는다**(`ON CONFLICT DO NOTHING`). 사람이 확정한 값(`user_confirmed`)을 yaml 기본값으로 되돌리면 FR-05b가 무너진다.
- **`execution_logs`에 `class_name` 컬럼 추가**. `object_id`(런타임 인스턴스)로는 `object_attributes`를 조인할 수 없어 ERD의 의도가 성립하지 않았다 — 시스템명세서 2.2·2.3절을 함께 갱신했다.
- `objects.yaml`에 `steel_can`·`paper_cup`을 잠정 추가(mock 픽스처와 짝). 최종 목록은 트랙 A(D-7)에서 확정.

**B0에서 하지 않은 것**: `web` 컨테이너 기동. `web/Dockerfile`은 ROS2 베이스에 colcon 빌드가 필요한데, 그 내용물(`ros_bridge.py` 등)이 B2에서 결정되므로 B2로 미룬다. 계획 초안의 "`up db planner web`"은 "`up db planner`"로 수정한다.

#### B1. planner 코어 — ✅ 완료 (2026-09-03)

**검증 결과**: mock 5종 스모크 테스트 5/5 통과(`scripts/check_plan_fixtures.py`, 실제 LLM 호출), 검증기 단위 테스트 17건 통과(`planner/tests/test_validator.py`), 재계획 경로 확인(직전 실패 물체를 건너뛰고 나머지 재계획).

**B1에서 내린 결정**

- **LLM이 정하는 것과 코드가 정하는 것을 분리**했다. LLM은 `{skill, object_id, bin_id}`만 출력하고, 파지 자세(후보 중 최고점)와 제어 프로파일은 검증기가 채운다. 좌표·파지력은 물리적 안전에 직결되므로 LLM 출력에 맡기지 않는다(NFR-03a).
- **모델은 `gpt-4o`**. 보유 키로 조회한 사용 가능 모델이 `gpt-4o`/`whisper-1` 두 개뿐이다(`whisper-1`은 6단계 STT의 선택지가 된다). `OPENAI_MODEL`로 교체 가능.
- **프롬프트 버전을 DB에 기록**한다(`prompt_version`). 아래 프롬프트 수정 이력이 `task_sequences`에 `plan-v1`/`plan-v2`로 남아 있어 버전별 비교가 가능하다(NFR-09).

**스모크 테스트가 잡아낸 프롬프트 결함 2건** (plan-v1 → plan-v2)

1. 파지 불가 물체가 하나 섞이자 LLM이 **지시 전체를 거부**했다 → "일부만 수행 가능하면 가능한 부분만 시퀀스로 만든다" 규칙 추가.
2. 미확인 신규 클래스를 **시퀀스에서 통째로 제외**했다 → FR-05b는 "확인 전이라고 빼는 것"이 아니라 "보수적 프로파일로 다루는 것"이므로, 제외하지 말라는 규칙 추가.

2번은 처음에 테스트가 헛통과했다(그 물체가 아예 없으니 프로파일 검사가 돌지 않았다). 검사 항목에 "대상이 시퀀스에 존재하는가"를 먼저 넣어 고쳤다.

**발견한 인터페이스 공백**: `웹_인터페이스_정의서.md` 3절의 `/internal/plan` 요청에 활성 `SafetyEvent`를 전달할 필드가 없다. FR-12는 안전 이벤트를 검증기의 게이트 조건으로 요구하는데, `planner`는 ROS2를 모르므로 `web`이 실어 보내야 한다. `active_safety_events` 필드를 추가로 받도록 구현하고, 문서 8절 미확정 항목에 등록했다.

| 신규 물체 확인 (FR-05b) | 수동 | ✅ 대기 목록 → 수정 후 승인 → `user_confirmed` 반영, 재승인 409 |
| 재계획 (FR-16) | `MOCK_FAIL_OBJECT`로 실패 주입 | ✅ 같은 `trace_id`에 `sequence_id` 2건, 실패한 물체를 뺀 재계획 실행 |

**B2에서 내린 결정**

- **어댑터 경계는 `executor.py` 하나.** `MOCK_MODE`로 `MockExecutor`/`RosExecutor`를 교체하며, `rclpy` import는 `MOCK_MODE=0`일 때만 일어난다. `main.py`와 라우터는 ROS2를 모른다.
- **`web/Dockerfile`의 베이스는 B2 시점에 `python:3.12-slim`**. mock 모드에 ROS2가 필요 없고, `ros:jazzy` 베이스는 `sort_msgs` colcon 빌드까지 딸려와 개발 반복이 느려진다. B4에서 ROS2 베이스로 바꾼다 — 위 격리 덕분에 앱 코드는 그대로다.
- **trace 스냅샷은 메모리, 실행 기록은 DB.** 진행 상태는 수명이 짧고 재연결 폴백 용도라 메모리로 충분하다(단일 사용자 가정, 8절). 영속 기록은 `execution_logs`다.
- **실패 주입 스위치**(`MOCK_FAIL_OBJECT`)를 mock 어댑터에 뒀다. 재계획 경로는 실패가 나야만 지나가는데, 실물 로봇 없이 그 경로를 밟을 방법이 달리 없다.
- `executor.py`는 계획서의 4개 시그니처에 `stop()`/`home()`을 더한 6개다 — 2.6절의 직접 제어가 로봇에 도달하려면 같은 경계를 지나야 한다.

**E2E가 잡아낸 LLM 결함 1건** (plan-v2 → plan-v3): "전부 왼쪽 박스로 옮겨줘"에서 유리병(파손위험·투명)을 **조용히 누락**했다. 실패가 아니라 승인된 계획이 불완전한 것이라 아무도 오류를 보지 못한다 — 분류 정확도(BR 3.1절)를 직접 깎는 종류의 결함이다. "전부/모두 지시에서는 파지불가 외에 어떤 속성도 제외 사유가 아니다"를 프롬프트에 넣고, `check_plan_fixtures.py`에 "전부" 케이스를 추가해 회귀를 막았다.

이 결함은 B1의 5종 스모크 테스트를 통과한 상태에서 남아 있었다. 픽스처가 시나리오는 덮었지만 **"전부" 같은 지시어를 안 덮었기 때문**이고, B5 평가셋이 지시 표현별로 케이스를 나눠야 하는 이유다.

**B3에서 내린 결정**

- **런타임 이미지에 node를 넣지 않는다.** `web/Dockerfile`이 node 스테이지에서 빌드하고 `dist/`만 파이썬 런타임으로 복사한다. `package-lock.json`을 커밋해 이미지 빌드를 재현 가능하게 했다(NFR-09).
- **SPA 폴백은 모든 라우터 뒤에 마운트**한다. 순서가 뒤집히면 `/api`·`/ws`를 정적 파일 핸들러가 가로챈다.
- **이력 화면에는 WebSocket을 붙이지 않았다.** "예전에 뭘 했는가"는 수명이 긴 정보라 실시간 갱신이 필요 없고, 실시간 화면과 섞으면 둘 다 읽기 어려워진다(화면정의서 1절 원칙).
- **phase→진행률 매핑 테이블은 프론트가 갖는다**(2.2.8절). 액션 정의의 Feedback 상수를 키로 쓰므로 스킬에 phase가 추가되면 이 표도 함께 고쳐야 한다.

**발견한 인터페이스 공백 2건**

1. `GET /api/world-state`가 없었다 → 탐지 물체 목록이 최초 렌더에서 채워질 방법이 없다. WebSocket은 변화가 있을 때만 밀어주기 때문이다. (`웹_인터페이스_정의서.md` 2.7절 신설)
2. **실행 중 새로고침하면 진행 상황이 통째로 사라졌다** → `trace_id`가 명령을 보낸 페이지 메모리에만 있어서, 2.3절의 스냅샷 폴백을 호출할 키 자체가 없었다. `GET /api/traces`(최근 목록)를 추가하고 화면이 마운트 시 최근 trace를 채택하게 했다. (2.3절 갱신)

**미연결로 남긴 것**: 카메라·뎁스 뷰는 자리만 잡았다(D-5 스트림 방식 미확정). 마이크 버튼은 6단계(STT) 범위다.

`화면정의서.md`를 그대로 구현한다. 두 화면은 상태를 공유하지 않는다.

**B4에서 내린 결정**

- **`home`을 액션으로 신설**(`sort_msgs/action/Home.action`, 인터페이스_정의서 4.3절). 계획 시점에는 "스킬로 추가할지 별도 서비스로 둘지" 미정이었다. 액션으로 정한 근거는 2.6절이 정지를 "`mode`와 무관하게 항상 허용되는 유일한 엔드포인트"로 규정한다는 것이다 — 정지는 진행 중인 액션 goal 취소로 구현되므로, 서비스로 두면 **한번 시작하면 멈출 수 없는 수 초짜리 모션**이 생긴다. 인터페이스 모양을 정한 것은 관례가 아니라 이 요구다.
- **control 노드 5종을 한 프로세스로 띄운다**(`control/control/main.py`, `control_node`). `robot_state`의 소유자(`RobotStatePublisherNode.store`)가 하나여야 하는데, mode 전이는 액션 서버가 만들고 발행은 상태 노드가 한다. 프로세스가 갈리면 그 둘이 같은 메모리를 못 본다. 액션 실행이 상태 발행을 막지 않도록 `MultiThreadedExecutor`를 쓴다.
- **`web` 런타임 베이스를 `python:3.12-slim` → `ros:jazzy-ros-base`로 교체**했다(B2에서 예고한 지점). mock 모드와 ROS 모드가 **같은 이미지**를 쓴다 — 모드별로 이미지가 갈리면 `executor.py` 경계가 코드에만 있고 배포에는 없는 것이 된다. 빌드 컨텍스트를 저장소 루트로 올려 `sort_msgs`를 이미지 안에서 빌드한다.
- **ROS 모드 web은 별도 compose 서비스(`web_ros`, `profiles: ["ros"]`)**다. 코드 차이는 없고 **네트워크 모드만 다르다** — DDS 디스커버리가 멀티캐스트에 기대므로 브리지 네트워크에서는 호스트의 control을 찾지 못한다(control도 같은 이유로 이미 `network_mode: host`다). host 네트워크에는 서비스 이름 DNS가 없어 planner/db를 게시 포트로 부른다.
- **`request_id` 캐시 TTL을 60초로 확정**했다(인터페이스_정의서 7절 미확정 항목 해소). 재전송은 통신 실패 직후에 일어나므로 수십 초면 충분하고, 그보다 오래된 같은 ID는 재전송이 아니라 새 요청으로 보는 편이 안전하다.
- **`FAKE_FAIL_OBJECT`를 `pick_server`에 뒀다.** mock 어댑터의 `MOCK_FAIL_OBJECT`와 같은 자리·같은 이유다. 재계획은 실패가 나야만 지나가는 경로인데 fake 모드는 정의상 늘 성공한다. 두 경로가 같은 시나리오로 검증되지 않으면 어댑터 교체가 안전하다고 말할 수 없다.

**ROS2 경로로 바꾸자 드러난 결함 3건** — 셋 다 mock에서는 보이지 않는 종류였다.

1. **`/api/robot/home`이 모션 완료 후에야 202를 반환**했다. 2.6절의 202 `moving_home`은 "이동을 접수했다"는 뜻이지 "끝났다"가 아니다. 완료를 기다리면 홈이동 중 로봇이 busy라는 사실을 **아무도 관측할 수 없고**(응답 시점에 이미 끝나 있다), 2.1절 차단 규칙이 홈이동에 대해서는 실질적으로 없는 것이 된다. `/api/commands`와 같은 모양(백그라운드 태스크 + 즉시 202)으로 고쳤다. mock에서 안 보였던 이유는 `MockExecutor`가 상태를 메모리에 동기적으로 쓰기 때문이다 — 전파 지연이 0이라 블로킹이 무해해 보였다.
2. **`robot_state`를 변화와 무관하게 5Hz로 WebSocket에 중계**했다. control의 주기 발행(구독자가 언제 붙어도 현재 상태를 알아야 하므로 주기 발행이 맞다)을 그대로 흘려보낸 탓에, 아무 일도 없는 동안에도 모든 브라우저에 초당 5건이 나갔다. E2E 로그가 동일한 `mode=idle` 이벤트로 뒤덮여 드러났다. 브리지가 **변화분만** 올리도록 고쳤다(폴백 경로는 최신값을 그대로 읽으므로 새 접속 화면이 상태를 못 보는 일은 없다).
3. **RMW 불일치.** 워크스테이션 노드는 CycloneDDS인데 `ros:jazzy-ros-base`의 기본은 FastDDS다. 이 조합은 **`ros2 topic list`에 토픽이 뜨는데 구독 콜백이 한 번도 안 불리는** 형태로 실패한다(디스커버리는 되고 데이터는 안 흐른다). 이미지에 `rmw_cyclonedds_cpp`를 넣고 `RMW_IMPLEMENTATION`을 고정했다. 추가로 이 워크스테이션은 Cyclone을 `lo` 인터페이스로 고정해 두었는데, 그 설정 없이 뜬 컨테이너는 다른 인터페이스를 골라 같은 증상을 낸다 — 호스트 설정을 읽기 전용으로 마운트해 맞춘다(이미지에 굽지 않는다: 어느 인터페이스를 쓸지는 배포 환경의 정책이지 앱의 성질이 아니다).

**B4에서 하지 않은 것**: `control`의 실물 모션. `pick`/`place_into`/`home` 모두 `FAKE_ROBOT=0`이면 `NotImplementedError`를 던진다 — MoveIt2·`compliance.py` 연결은 M5의 일이다. `robot_state.joint_state`도 fake에서는 비어 있다(doosan-robot2 드라이버 연결 지점에 TODO).

**B5에서 내린 결정**

- **평가셋을 시나리오가 아니라 지시 표현으로 나눴다.** 계획서의 5개 카테고리(정상/모호/미검출/가반하중/작업공간)는 유지하되, 정상 지시를 단일 대상·복수 열거·전량("전부"/"모두"/"다")·속성 기반(긍정/부정)으로 쪼갰다. B2의 결함이 시나리오가 아니라 지시어에서 나왔기 때문이다 — 픽스처만 나누면 같은 종류를 또 놓친다.
- **채점은 승인 여부가 아니라 시퀀스 내용으로 한다.** `pick_objects`·`bins`·`profiles`를 대조한다. "승인했는가"만 보면 엉뚱한 물체를 옮기는 계획도 명령 정확도에 잡히지 않는다.
- **불가능 케이스는 상태가 아니라 불변식으로 채점한다.** 가반하중·작업반경 케이스의 "전부" 지시는 승인/거부가 갈릴 수 있으므로(아래 비대칭), "불가능한 물체가 승인된 계획에 들어 있지 않다"로 채점한다.
- **채점기는 planner 컨테이너에서 돈다.** `tests/`와 같은 이유로 `eval/`을 이미지에 굽는다 — psycopg와 `DATABASE_URL`이 거기 있어야 `eval_runs` 기록까지 한 번에 끝난다. 호스트에서 돌리면 "점수는 냈는데 기록이 안 남는" 상태가 조용히 생긴다(실제로 첫 실행이 그랬다).
- 픽스처 2종 신설: `world_state_overweight.json`(7200g), `world_state_out_of_workspace.json`(958mm). 기존 5종에 없던 조건이다.

**평가셋이 잡아낸 결함 2건** (plan-v3 → plan-v4) — 둘 다 **모호한 지시를 추측으로 실행**했다.

1. "그거 좀 치워줘" → 3개 **전부**를 옮기는 계획을 승인했다. B2에서 "전부 지시의 누락"을 고치려 넣은 규칙 6-1의 압력이 **대상이 불분명할 때도 전부를 고르는 쪽**으로 새어 나온 것으로 보인다. 한쪽을 고친 프롬프트 규칙이 반대쪽 결함을 만든 형태다.
2. "유리병 좀 저기에 넣어줘" → 목적지를 **임의로** 정해 승인했다.

규칙 7-1(모호함을 "전부"로 넓히지 않는다)·7-2(목적지도 같은 기준)를 넣어 고쳤고, **규칙을 넣기 전에 반대 방향 케이스를 먼저 추가**했다(물체가 하나뿐일 때의 "그거"는 승인되어야 한다). 과잉 거부로 넘어가는 것을 잡기 위해서다.

**함께 드러난 설계상의 비대칭**: "전부 옮겨줘"에서 가반하중 초과 물체는 LLM이 스스로 빼고 부분 계획을 만드는데(무게는 프롬프트에 들어간다), 작업반경 밖 물체는 시퀀스 전체가 거부된다(좌표는 일부러 넣지 않아 LLM이 알 수 없고, 검증기에는 부분 거부가 없다). 둘 다 안전하지만 도달 불가 물체 하나가 나머지를 막는다. 대응 방향은 리포트 4절에 적었다 — 좌표 대신 도달 가능 불린을 프롬프트에 넣는 쪽이 기존 원칙을 깨지 않는다.

**B5에서 하지 않은 것**: 평가셋의 물체 이름은 `glass_bottle`/`steel_can`/`paper_cup`이라 트랙 A가 학습한 3종(`suncream`/`tape`/`nail_product`)과 다르다(D-7). 지시 표현·거부 논리는 클래스와 무관하지만 물체 이름을 쓰는 케이스의 문구는 클래스 확정 시 갱신하고 `DATASET_VERSION`을 올려 다시 측정해야 한다. 같은 클래스가 여러 개 있어 "캔"이 둘을 가리키는 케이스도 아직 없다.
