# 화면 정의서: web 프론트엔드

`web` 프론트엔드가 실제로 어떤 화면으로 구성되고, 각 화면의 요소가 어떤 인터페이스(REST/WebSocket/ROS2)에서 데이터를 받는지 정의한다. 레이아웃 목업은 대화 중 렌더링된 것을 기준으로 한다.

| 항목 | 내용 |
|---|---|
| 문서 버전 | v1.2 (2026-09-10 — 상태바 TCP 표시, 도메인 선택 버튼, 웨이크워드 경로 개정, 학습 데이터 화면 2탭 구조 반영) |
| 관련 문서 | `웹_인터페이스_정의서.md`, `인터페이스_정의서.md`(sort_msgs), 시스템명세서 |

**화면 구성 원칙**: 실시간 제어 화면과 이력 화면을 완전히 분리한다. "지금 무슨 일이 일어나는가"(실시간, 짧은 수명)와 "예전에 뭘 했는가"(이력, DB 조회, 긴 수명)를 한 화면에 섞으면 둘 다 읽기 어려워진다.

---

## 1. 화면 목록

| 화면 | 경로(예시) | 성격 |
|---|---|---|
| 제어 화면 | `/` | 실시간, WebSocket 기반, 단일 사용자 가정 |
| 이력 화면 | `/history` | 정적 조회, REST 폴링/새로고침 기반 |
| 학습 데이터 화면 (2026-09-08 추가) | `/datasets` | 정적 조회. 검출기 데이터셋(Roboflow 스타일 수집+큐레이션+내보내기) / 그랩 데이터 두 탭. 학습 트리거 없음 |

세 화면은 상단 네비게이션 링크로만 연결되고, 상태를 공유하지 않는다 — 각자 자체적으로 REST를 호출해 독립적으로 그린다.

## 2. 제어 화면

### 2.1 레이아웃 영역

```
┌─────────────────────────────────────────────────────────┐
│ 타이틀                        [이력 보기 →] [데이터셋 →]  │  상단 네비
├─────────────────────────────────────────────────────────┤
│ ● Idle  현재 스킬 없음   TCP 설정됨        연결됨          │  상태바
├─────────────────────────────────────────────────────────┤
│ ⚠ (조건부) 안전 이벤트 배너                                │  안전 배너
├───────────────────────────┬─────────────────────────────┤
│ [카메라 뷰]  [뎁스 뷰]      │ 탐지 물체 목록                │
│                           │ ─────────────                │
│                           │ [홈 이동]      [정지]         │  메인 그리드
├───────────────────────────┴─────────────────────────────┤
│ 현재 작업 — "명령 텍스트"                                  │
│  Pick — 물체명       [██████████░░] 검증 중                │  작업 진행도
│  Place into — 목적지 [░░░░░░░░░░░░] 대기 중                │
├─────────────────────────────────────────────────────────┤
│ [가정] [약국] [재활용]                                     │  도메인 선택
│ [명령 입력창 · 마이크 · 전송]                              │  명령 입력
│ (비활성 시) 사유 문구                                       │
└─────────────────────────────────────────────────────────┘
```

### 2.2 컴포넌트별 정의

#### 2.2.1 상단 네비게이션

| 요소 | 내용 | 데이터 출처 |
|---|---|---|
| 타이틀 | 정적 텍스트 | — |
| 이력 보기 링크 | `/history`로 이동 | — |
| 데이터셋 링크 | `/datasets`로 이동 | — |

#### 2.2.2 상태바

| 요소 | 내용 | 데이터 출처 |
|---|---|---|
| 모드 배지 | `idle`(초록)/`busy`(파랑)/`error`(주황)/`estopped`(빨강), 점+텍스트 | WebSocket `robot_state.mode` |
| 현재 스킬 | "No active skill" 또는 `current_skill` 값 | WebSocket `robot_state.current_skill` |
| TCP 표시 (2026-09-09 추가) | "TCP 설정됨" / "TCP 설정 안 됨"(강조). 툴팁에 실제 TCP 이름 | WebSocket `robot_state.tcp_configured`·`tcp_name` |
| 연결 상태 | WebSocket 연결 여부 | 프론트 자체 상태(연결 끊김 시 "연결 끊김"으로 전환, 재연결 시도) |

**TCP 표시가 왜 상태바에 있나**: 컨트롤러의 TCP(`GripperDA_v1`)가 풀리면 `get_current_posx`가 플랜지를 보고하게 되어 **좌표 전체가 약 208mm 조용히 어긋난다** — 화면 어디에도 오류가 뜨지 않고 파지만 빗나간다. 실제로 몇 세션 동안 원인을 못 찾은 사고가 있었고(`docs/problem/2026-09-07-grasp-coordinate-offset.md`), 그 재발을 눈으로 즉시 잡으려고 둔 표시다. 값이 아니라 **설정이 살아 있는지**만 본다.

#### 2.2.3 안전 배너

| 요소 | 내용 | 데이터 출처 |
|---|---|---|
| 배너 (조건부, `severity=critical`일 때만 노출) | 아이콘 + `description` | WebSocket `safety_event` |
| 해제 | `requires_manual_reset=false`이거나 새로운 `robot_state.mode=idle` 수신 시 자동 숨김 | — |

**우선순위**: 다른 모든 WebSocket 이벤트보다 먼저 렌더링·먼저 눈에 띄어야 한다(`웹_인터페이스_정의서.md` 4절 원칙). `severity=warning`은 배너 대신 상태바 옆 작은 아이콘으로 축소 표시(토스트 등으로 격하하지 않음 — 놓치면 안 되므로 상시 배치, 다만 크기만 작게).

#### 2.2.4 관측 뷰 (개정 — 온디맨드 전환, `docs/on-demand-perception.md` D-5)

*원안(RGB 원본 스트림, 오버레이 없음)은 이후 사용자 요청으로 뒤집혔고, 온디맨드 전환에서
그 결정을 재확인했다. `탐지 물체 목록`(옛 2.2.5절)을 화면에서 없애는 대신, 그 물체들이
무엇에 근거해 판단됐는지를 이 뷰로 남긴다 — "캡처 사진 + 세그멘테이션 + 파지 후보 그립
모양"이 요구사항이었다.*

| 요소 | 내용 | 데이터 출처 |
|---|---|---|
| 관측 뷰 | `grasp`가 합성한 오버레이 — 캡처 사진 위에 마스크 윤곽 + 파지 후보 그립 모양(팜·손가락) | `/grasp/debug_image` (`grasp/node.py:_publish_debug_image`) → `web`이 MJPEG로 중계 (`GET /api/camera/color`) |
| 뎁스 뷰 | 뎁스 맵 시각화(컬러맵), 원본 그대로 | 동일 경로, `GET /api/camera/depth` |
| 관측 시각 | "n초 전 관측" | `WorldState.stamp` (`GET /api/world-state`, WebSocket `world_state` 이벤트) |

**온디맨드 전환 이후 이 화면은 명령 사이에 멈춰 있는 것이 정상이다** — perception이 더
이상 주기 발행하지 않고 명령을 받은 순간에만 관측한다(`인터페이스_정의서.md` 2.0절 개정).
관측 시각을 함께 보여주는 이유가 그것이다 — 없으면 멈춘 그림을 오래된 것으로 오해하거나
방금 온 것을 못 알아본다.

#### 2.2.5 탐지 물체 목록 (2026-09-08 재도입)

`인식된 물체 (N)` 목록(`web/frontend/src/components/ObjectList.tsx`)이 최신 `world_state`
스냅샷을 보여준다 — `name_ko`, 파지력 단계 배지(g1~g5), `needs_confirmation=true`일 때
붙는 "신규" 배지(등록되지 않은 클래스라 `fallback`으로만 다뤄진다는 안내). 2.2.7이 정의하던
확인 모달·"확인 대기" 패널은 2026-09-09 제거했다(해당 절 참조) — 지금 "신규" 배지는
클릭해도 아무 동작이 없는 순수 안내용이다.

#### 2.2.6 로봇 직접 제어 버튼

| 요소 | 내용 | 데이터 출처 / 동작 |
|---|---|---|
| 홈 이동 | `robot_state.mode !== 'idle'`이면 비활성화 | `POST /api/robot/home` (`웹_인터페이스_정의서.md` 2.6절) |
| 정지 | **항상 활성화** — mode와 무관 | `POST /api/robot/stop` (2.6절, busy 차단 규칙의 예외) |

정지 버튼은 위험 강조 스타일(빨강 계열 테두리/텍스트)로 시각적으로 구분한다 — 다른 버튼과 같은 톤이면 급할 때 못 찾는다.

#### 2.2.7 (제거됨) 신규 물체 확인 모달 (FR-05b)

`GET`/`POST /api/object-confirmations`로 열던 확인 모달(`ConfirmModal.tsx`)과 "확인 대기" 패널(`PendingConfirmations.tsx`)을 2026-09-09 제거했다 — 저장 지점인 planner의 `vlm_client.py`가 끝까지 TODO 스텁이었고, 이 모달을 통해 실제로 값을 확정한 적이 없었다(시스템명세서 3.1a절). 등록되지 않은 클래스는 여전히 확인 없이 `fallback`(5=가장 약하게)으로만 다뤄진다 — 2.2.5의 "신규" 배지가 그 상태를 보여준다.

아래 2.2.7a의 **라벨 수정**은 이것과 별개 기능이라 그대로 남는다 — 명령 실행 직전 물체 하나의 라벨을 즉석에서 고치는 것이지, 클래스 속성을 DB에 확정하는 절차가 아니다.

#### 2.2.7a 실행 승인 모달 (2026-09-08 추가)

검증기를 통과한 시퀀스도 로봇이 움직이기 전에 뜬다(명령 1건당 1회) — 신규 물체 확인(제거된 2.2.7)과 달리 이건 **실행 승인**이다. 떠 있는 동안 `POST /api/commands`는 `409 AWAITING_APPROVAL`로 새 명령을 거부한다(2.1절과 별개 조건 — 로봇 mode는 그대로 idle이다).

| 요소 | 내용 | 데이터 출처 |
|---|---|---|
| 계획된 스텝 목록 | 스킬 + 물체 이름 + 목적지, 물체별 파지력 단계 배지(g1~g5) | WebSocket `execution_approval_needed`의 `steps` |
| 판단 근거 | 물체별 VLM 판단 근거 한 줄(`reasoning`), `attr_source=llm_suggested`일 때만 표시 | 같은 이벤트의 `objects` |
| 검증 상태 배너 | `validation_status`/`validation_reason` | 같은 이벤트 |
| 라벨 수정 | 물체별 class_name/name_ko를 고쳐 재계획 요청 | `POST .../approval` `{action: "correct_label", object_id, class_name, name_ko}` — 응답 대신 같은 이벤트가 갱신된 내용으로 다시 온다 |
| 승인/거부 버튼 | 승인 시 실행 재개, 거부 시 `execution_result`(`failure_reason: "user_rejected"`)로 종료 | `POST .../approval` `{action: "approve"}` / `{action: "reject"}` |

#### 2.2.8 작업 진행도

| 요소 | 내용 | 데이터 출처 |
|---|---|---|
| 현재 명령 텍스트 | `command_text` | `GET /api/traces/{trace_id}` 또는 명령 전송 시 로컬 보관 |
| 스텝별 진행바 | 스킬명 + 물체/목적지 + `phase` 텍스트 | WebSocket `execution_progress`(`phase`), `execution_result`(완료 시) |
| 진행바 채움 정도 | `phase` 값을 스킬별 4단계로 매핑(예: `pick`은 approaching=25%/contact_detected=50%/lifting=75%/verifying=90%, 완료 시 100%) | 프론트 자체 매핑 테이블 |
| 시퀀스 없음 상태 | "대기 중인 작업이 없습니다" | — |

#### 2.2.9 명령 입력창

| 요소 | 내용 | 데이터 출처 |
|---|---|---|
| 텍스트 입력 | 자연어 명령 | `POST /api/commands` |
| 마이크 버튼 | 클릭 시 녹음 시작/종료, 종료 시 `/api/stt` 호출 → 결과를 입력창에 채움(자동 전송 아님, FR-24) | `POST /api/stt` |
| 시나리오 버튼 (가정 / 약국 / 재활용) | **도메인 선택이다 — 누른다고 명령이 나가지 않는다.** 고른 도메인이 이후 보내는 모든 명령에 실려 가고(예시 문구는 입력창에 채워 준다), 백엔드가 그 값으로 VLM 프롬프트를 분기한다. 기본값은 '가정'(`general`) | `POST /api/commands`의 `domain` |
| "hello rokey" 웨이크워드 (2026-09-09 개정) | **브라우저가 아니라 로봇 PC 마이크가 듣는다.** `tools/voice/wakeword_bridge.py`가 감지하면 `/ws/live`로 `wake_word_detected`가 오고, 그 순간 브라우저가 마이크 버튼을 누른 것처럼 자동 녹음(고정 4초) → `/api/stt`. 감지된 순간을 잠깐 표시해 준다 — 없으면 "문구가 걸린 건지 마이크만 켜진 건지" 구분이 안 된다 | WebSocket `wake_word_detected` |
| 전송 버튼 | `robot_state.mode !== 'idle'`이면 비활성화 | `POST /api/commands` |
| 비활성 사유 문구 | "로봇이 동작 중입니다 — 완료 후 다시 시도하세요" (mode별로 문구 분기: busy/error/estopped) | `robot_state.mode` |

`low_confidence=true`(STT 신뢰도 0.8 미만, `웹_인터페이스_정의서.md` 2.2절)면 입력창에 채우되 "인식이 불확실합니다. 확인 후 전송하세요" 경고를 같이 표시한다.

**웨이크워드를 브라우저에서 걷어낸 이유**: 처음에는 브라우저 `SpeechRecognition`(Web Speech API)을 상시 대기로 돌렸는데, 사전에 없는 단어("rokey")를 신뢰성 있게 잡지 못했다(2026-09-09 실측). 로봇 PC 마이크를 openwakeword 커스텀 모델로 직접 듣는 쪽이 훨씬 안정적이라 그 경로로 옮겼고, 브라우저 쪽 토글은 제거했다. **녹음과 STT 자체는 여전히 브라우저 마이크가 한다** — 웨이크워드만 옮겨 왔다.

## 3. 이력 화면

### 3.1 레이아웃

```
┌─────────────────────────────────────────────────────────┐
│ 이력                                        [← 제어 화면]  │
├─────────────────────────────────────────────────────────┤
│ 필터: [기간] [결과: 전체/성공/실패] [스킬: 전체/pick/.../home/stop] │
├─────────────────────────────────────────────────────────┤
│ 시각        명령/스킬          결과   파지전략    │
│ ─────────────────────────────────────────────── │
│ 09-03 05:11 "깨지기 쉬운 것만..." 성공  contact_gr..  │  › 상세
│ 09-03 05:09 stop                 —     —          │  › 상세
│ ...                                                       │
└─────────────────────────────────────────────────────────┘
```

### 3.2 컴포넌트별 정의

| 요소 | 내용 | 데이터 출처 |
|---|---|---|
| 필터 | 기간, 결과(성공/실패), 스킬 종류(`pick`/`place_into`/`home`/`stop`) | 프론트 상태, `GET /api/executions` 쿼리 파라미터로 전달(쿼리 파라미터 확장 필요 — 6절 참조) |
| 목록 행 | 시각, 명령 텍스트(`stop`/`home`은 명령 텍스트 없이 스킬명만), 결과, `grasp_strategy` | `execution_logs` (`GET /api/executions`) |
| 상세 (행 클릭 시 펼침) | 같은 `trace_id`의 전체 스텝, `torque_trace` 요약, `bin_id`, `retry_count`, `cycle_time_ms` | `GET /api/traces/{trace_id}` 또는 `execution_logs` 상세 |

**`stop`/`home` 이력도 같은 테이블에 섞여 나온다** — `command_text`가 없는 행으로 표시하고 스킬명(`stop`/`home`)을 대신 보여준다. 별도 탭으로 분리하지 않는다. 분류 작업과 로봇 직접 제어를 시간순으로 같이 봐야 "정지 버튼을 왜 눌렀는지" 맥락 파악이 쉽다.

### 4.2 검출기 데이터셋 탭

| 요소 | 내용 | 데이터 출처 |
|---|---|---|
| 필터 | 클래스명, 기간 | 프론트 상태 → `GET /api/datasets` 쿼리 파라미터 |
| 갤러리 카드 | 썸네일 + 그 사진에 있는 물체 이름 요약(같은 클래스가 여럿이면 `치약 x2`), 수집 시각, 검토 여부 | `GET /api/datasets` → `GET /api/datasets/{trace_id}/image` |
| 어노테이션 오버레이 | 썸네일·상세 위에 물체별 폴리곤을 겹쳐 그린다 | `GET /api/datasets/{trace_id}/annotations` (0~1 정규화 좌표) |
| 검토 표시 | 항목 하나 또는 선택 여러 개를 검토됨으로 표시하고 라벨을 고친다 | `POST /api/datasets/{trace_id}/review`, `POST /api/datasets/bulk-review` (web → planner 중계) |
| 내보내기 | 검토된 항목을 YOLO 학습셋 형식으로 받는다 | `GET /api/datasets/export` |

**카드 단위가 물체가 아니라 사진이다**(2026-09-09 변경). `dataset_items`는 물체 단위 행이지만 같은 `trace_id`는 같은 사진이므로, 사진 하나를 카드 하나로 묶고 그 안의 물체들을 함께 보여준다 — 큐레이션은 "이 사진을 학습에 쓸 것인가"의 단위로 하는 편이 자연스럽다.

### 4.3 그랩 데이터 탭 (2026-09-09 추가)

| 요소 | 내용 | 데이터 출처 |
|---|---|---|
| 필터 | 결과(성공/실패), 클래스명, 전략 | `GET /api/grasp-attempts` 쿼리 파라미터 |
| 목록 행 | 시각, 물체, 전략(`PCA(휴리스틱)`/`GraspNet`/`Contact-GraspNet`), 실행한 파지 자세, 성공/실패 | `execution_logs` (`GET /api/grasp-attempts`) |
| 내보내기 | 필터가 걸린 그대로 JSON | `GET /api/grasp-attempts/export` |

**GraspNet 원 데이터셋에는 못 미치는 최소 신호다** — 그 수준이 되려면 실행 하나당 후보 여러 개를 다 채점해야 한다. 지금 있는 것은 "실제로 실행한 후보 하나와 그 결과"뿐이고, 그것만으로 할 수 있는 분석(전략별·클래스별 성공률)에 쓴다.
